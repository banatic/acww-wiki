# 에이커 격자
<!-- source: wiki/systems/acre-grid.md -->

**요약.** 마을의 지면은 에이커로 이루어진 2차원 배열 하나이며, 각 에이커는 16비트 타일 id로 구성된 독립적인 16x16 레이어를 최대 두 개 가진다. 게임은 타일을 직접 인덱싱하지 않는다. 모든 읽기와 쓰기는 월드 위치를 에이커 좌표와 에이커 내부 타일 좌표로 나누고 두 좌표의 범위를 검사하는 작은 접근자 계열을 거친다. 이 계열은 두 바이트를 가리키는 포인터를 반환하거나, 게임에서 보통 "맵 밖"을 뜻하는 널 포인터를 반환한다. 위치 분할의 단위는 두 시프트로 정해진다. 타일은 위치 단위로 `1 << 13`, 에이커는 `1 << 17`이므로 에이커 한 변은 정확히 16타일이다. 이 문서는 접근자들이 드러내는 데이터 모델을 다룬다. 마을을 이루는 요소와 세이브 내 저장 위치는 `town.md`에서 다룬다.

## 무슨 일이 일어나는가

이 계열 전체는 `(grid, position, layer) -> u16 *`라는 하나의 조합된 질문으로 환원된다. 진입점 `func_0204f5a8`은 격자 객체, 위치 레코드 포인터, 레이어 번호를 받아 네 워드짜리 임시 배열을 0으로 만들고, 위치를 그 배열에 풀어 쓴 뒤 분해한 좌표 네 개로 요소 접근자를 호출한다 [S: func_0204f5a8, main, src/matched/func_0204f5a8.c].

분해는 두 함수가 맡는다. `func_0204f828`은 인자 형태를 맞추는 어댑터로, 두 목적지에서 유도한 네 목적지 `(a, a + 4, b, b + 4, source)`로 `func_0204f840`을 호출한다 [S: func_0204f828, main, src/matched/func_0204f828.c]. 이어서 `func_0204f840`은 소스 레코드에서 정확히 두 워드, 즉 `+0`과 `+8`의 워드를 읽어 네 값을 쓴다. 첫 번째 쌍에는 `word0 >> 17`과 `word8 >> 17`, 두 번째 쌍에는 `(word0 >> 13) & 0xf`와 `(word8 >> 13) & 0xf`를 쓴다 [S: func_0204f840, main, src/matched/func_0204f840.c]. 두 시프트 모두 산술 시프트이므로 음수 좌표는 음수 에이커 인덱스를 만들고, 요소 접근자의 부호 없는 범위 검사가 이를 거부한다 [S: func_0204f5e0, main, src/matched/func_0204f5e0.c].

`+0`과 `+8`을 읽고 `+4`는 전혀 읽지 않는다는 점이 소스 레코드의 정체를 알려 준다. 멤버가 `x`, `y`, `z`이고 `y`가 수직축인 NNS `VecFx32`이므로, 격자는 `x`와 `z`로 인덱싱하고 높이 워드는 건너뛴다는 해석이다 [S: func_0204f840, main, src/matched/func_0204f840.c] [H: the VecFx32 reading is inferred from the two offsets and the SDK's vector layout, not from a
named type in the ROM; the experiment that would settle it is in Hypotheses].

`func_0204f5e0`은 요소 접근자다. 에이커 `x`가 격자 너비보다 작고 에이커 `z`가 높이보다 작으며 격자 베이스 포인터가 널이 아닐 때만 호출을 받아들인다. 그런 다음 `base + (x + z * width) * 0x28`을 인덱싱해 해당 요소를 타일 가져오기 함수에 전달한다 [S: func_0204f5e0, main, src/matched/func_0204f5e0.c]. 따라서 에이커는 `0x28`바이트 레코드이고, 에이커 배열은 너비를 스트라이드로 하는 행 우선 배열이다.

`func_02037e0c`은 타일을 가져오는 가장 안쪽 본체이며 유일한 ARM 본체다. 레이어가 2보다 작고 두 타일 좌표가 모두 `0x10`보다 작아야 호출을 받아들인다. 에이커 요소의 `+0x18 + layer * 4`에서 레이어 포인터를 읽고, 널이면 0을 반환하며, 그렇지 않으면 `layer_base + ((tx + (tz << 4)) << 1)`을 반환한다 [S: func_02037e0c, main, src/matched/func_02037e0c.c]. 레이어 두 개, 16x16타일, 타일당 두 바이트이며 `tz`가 행이다. 레이어 하나는 512바이트이고 에이커 요소는 타일 자체 대신 레이어 포인터 두 개를 담으므로, 한 레이어만 있고 다른 레이어는 없는 에이커도 유효하다.

**널 반환은 오류가 아니라 정상적인 결과다.** 에이커 범위, 타일 범위, 레이어 범위라는 세 가지 별도 검사가 이를 만들 수 있으며, 모든 호출자는 포인터를 쓰기 전에 검사한다 [S: func_02037e44 and func_02037da8, main, src/matched/func_02037e44.c and
src/matched/func_02037da8.c]. PROMOTE77은 그 비율을 측정했다. `func_02037e0c`과 `func_0204f5e0` 각각의 기록된 호출 512회 중 64회는 검사에 실패해 인덱스를 계산하지 않고 0을 반환했다 [E: docs/log/cycle42-save.md `## PROMOTE77` P77-3].

**쓰기 경로는 마지막에 저장을 수행하는 같은 순회이며, 별도 계열이다.** `func_0204f538`은 타일 공간의 `(x, z)`를 받아 에이커는 `x >> 4`, 타일은 `x - ((x >> 4) << 4)`로 직접 분할한 다음 `func_0204f564`를 호출한다 [S: func_0204f538, main, src/matched/func_0204f538.c]. `func_0204f564`는 `func_0204f5e0`의 세 검사와 `* 0x28` 인덱싱을 그대로 반복하고 `func_02037e44`를 호출한다. 이 함수는 타일 가져오기를 호출하고 반환된 포인터를 통해 16비트 값 하나를 저장한 뒤 1을 반환하며, 포인터가 널이면 0을 반환한다 [S: func_0204f564 and func_02037e44, main, src/matched/func_0204f564.c and
src/matched/func_02037e44.c]. 따라서 읽기와 쓰기 계열이 공유하는 것은 타일 가져오기뿐이며, 범위 검사 로직은 두 곳에 존재한다.

**`func_02037d14`는 역변환이며 타일 인덱스의 방향을 확정한다.** 인덱스를 받아 `i & 0xf`와 `(i >> 4) & 0xf`를 쓰는데, 이는 타일 가져오기의 `tx + (tz << 4)`를 정확히 역변환한 것이다 [S: func_02037d14, main, src/matched/func_02037d14.c]. `func_02037da8`이 이를 사용한다. 에이커 레이어의 타일 0을 가져와 `0x100`개 타일 전체를 순방향으로 훑으면서 호출자가 준 `[lo, hi]` 범위의 첫 id를 찾고, 발견한 인덱스를 좌표 쌍으로 되돌린다 [S: func_02037da8, main, src/matched/func_02037da8.c]. 이 순회는 한 레이어가 연속된 타일 256개라는 사실을 독립적으로 확인하는 두 번째 근거이기도 하다.

**격자 객체에는 단위가 다른 두 크기가 있으며, 둘을 혼동하면 실제 문제가 생긴다.** `func_0204f5e0`과 `func_0204f564`는 `+4`, `+8`에서 너비와 높이를 읽어 에이커 좌표와 비교한다 [S: func_0204f5e0, main, src/matched/func_0204f5e0.c]. 맵 순회 `func_02046df4`는 `+0xc`, `+0x10`에서 크기 쌍을 읽고 타일 좌표로 반복하며, 매번 에이커 좌표를 `x >> 4`, 타일 좌표를 `x - ((x >> 4) << 4)`로 유도한다 [S: func_02046df4, main, src/matched/func_02046df4.c]. 따라서 두 쌍은 16:1 관계이며 서로 바꿔 쓸 수 없다.

**이는 대화의 비용이 아니라 마을이 매 프레임 요구하는 비용이다.** PROMOTE77은 주민 대화 1,200프레임 구간에서 다섯 접근자가 인터프리터 스텝의 7.22%를 차지한다고 측정했다. 이들을 승격했을 때 대화창을 닫은 조용한 구간의 감소폭(8.15%)이 대화 구간의 감소폭(7.63%)보다 더 컸는데, 대화에서는 글꼴 작업 때문에 이들의 비중이 낮아지기 때문이다 [E: docs/log/cycle42-save.md `## PROMOTE77` P77-6/P77-7]. 부팅의 프레임 58 맵 순회는 그 한 프레임에서 `func_0204f5e0`과 `func_02037e0c`을 각각 43,613회, 43,642회 실행한다 [E: docs/log/cycle42-save.md `## PERF72` P72-6, re-measured in `## PROMOTE77` P77-2].

## 확인 방법

가장 저렴한 실행 중 검사는 승격 기록기다. 선택한 함수의 모든 읽기와 쓰기를 주소와 함께 기록하므로, 위 스트라이드를 추론하지 않고 직접 출력한다. 프레임당 수만 번 실행되는 부팅 맵 순회에서 타일 가져오기를 기록한다.

    python -B scratchpad/promote90/rec90.py tilefetch 0x02037e0c 256 --scene boot
    python -B scratchpad/promote90/dumprec90.py scratchpad/promote/tilefetch/tilefetch.rec --summary

예상 결과: 모든 레코드가 `hostcalls=0 flags=0x00000000 steps=14`이며, 서로 다른 로드 주소가 에이커 요소마다 `0x18`과 `0x1c` 쌍으로 나타나고 레이어 읽기는 `0x200`바이트 간격이다 [E: the same instrument produced scratchpad/promote90/events-summary.txt for a different function
this way]. 기록기를 켜기 전에 `docs/kb/hybrid/promotion.md`의 1절을 읽는다. 기록된 LOAD에는 주소와 너비가 있고 값은 없으므로, 로드 값을 검사하는 코드는 아무 경고 없이 0을 읽게 된다 [E: port/interp/interp_cpu.c `REC_LOAD`, measured in docs/log/cycle42-save.md `## PROMOTE90`].

정적 검사는 `scratchpad/promote90/callers90.py`다. 주소를 대상으로 하는 모든 재배치 항목을 호출 지점을 소유한 심볼로 해석한다. `src/matched/` 검색에는 매칭된 본체만 보이므로, 이것이 유일하게 완전한 호출자 목록이다.

## 가설

- **위치 레코드는 `VecFx32`다.** 근거는 명명된 타입이 아니라 두 오프셋(`+0`, `+8`)과 SDK의 멤버 순서다. 대화 씬에서 승격 기록기로 `func_0204f840`을 기록하고, 두 씬의 호출 512회에서 소스의 `+4` 워드를 한 번도 읽지 않는지 확인하면 확정할 수 있다.
- **에이커 요소의 처음 `0x18`바이트.** 알 수 없다. `func_0204f5e0`의 호출자 87개 중 하나를 기록하고, 접근자가 반환한 포인터(같은 요소)에 접근하는 오프셋을 나열하면 확정할 수 있다.
- **`src/matched/func_0204f5a8.c`와 `port/build/shadow/func_0204f5a8.c`는 서로 다른 프로그램이다.** 매칭된 본체는 `void`이며 꼬리 호출이 반환하는 요소 포인터를 버린다. 섀도 본체는 이를 반환하고, 포트는 섀도를 링크한다. 둘 다 ROM의 꼬리 분기와 바이트 단위로 같으므로 바이트로는 판별할 수 없다. 이것이 **D2**이며, PROMOTE77은 차분 검사가 포인터를 버리는 본체를 512회 중 512회 일치(AGREEING)로 보고함을 측정했다 [E: docs/log/cycle42-save.md `## PROMOTE77` P77-4]. ROM 호출자가 어느 쪽을 원하는지 확정하려면 `func_0204f5a8`의 호출자 다섯 개가 반환 후 `r0`를 어떻게 쓰는지 읽는다.
- **에이커 너비가 6이 아닌 경우가 있는가.** `town.md`는 96x96타일 격자를 설명하므로 16x16타일 에이커가 6x6개인 셈이다. 그러나 이 계열은 매 호출마다 격자 객체에서 너비를 읽으며 결코 이를 가정하지 않는다. `func_0204f5e0`을 기록하고 `+4` 로드의 값을 읽으면 확정할 수 있다. 위 기록기 주의사항에 따라 이는 로드 로그 대신 저장 측이나 집계 측 계측을 써야 한다는 뜻이다.
