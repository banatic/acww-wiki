## 무엇인가

NAS의 리버스 프록시 뒤에서 실행되는 Python 프로세스 하나다. uvicorn 위의 FastAPI, 포트 하나, SQLite 파일 하나,
256 KB 세이브 이미지 디렉터리로 구성된다. 네 가지 일을 하며, 의도적으로 다섯 번째 일은 하지 않는다.

| 대상 | 위치 | 이유 |
|---|---|---|
| 계정 | `app/security.py`, `users` table | argon2id, HS256 토큰을 사용하며 잃을 세션 상태가 없다 |
| 클라우드 세이브 | `app/store.py`, `/data/saves/<user>/<version>.sav` | 블롭이 아닌 파일이다. 백업은 파일 복사이며, 손상된 행 하나가 마을을 망가뜨릴 수 없다 |
| 세이브 검증 | `app/savecheck.py` | `port/tools/savetool.py`에서 포팅한 ROM 자체의 수락 테스트다 |
| 로비 | `app/lobby.py`, 메모리 | 재시작 후에도 살아남은 로비는 그곳에 없는 사람들의 목록이다 |
| 릴레이 | `app/main.py` `/v1/relay/{room}` | 소켓 두 개와 `send_bytes`만 있으며, 서버는 프레임을 파싱하지 않는다 |

**TLS는 여기에 없다.** 서비스는 8080에서 일반 HTTP를 말하고 NAS의 리버스 프록시가 앞에서 HTTPS를 종료한다. 네트워크에
대해서는 상태가 없는 프로그램에서 인증서 수명 주기 하나를 줄이는 셈이며, Synology가 이미 인증서를 갱신한다.

**게임도 여기에 없다.** 이미지는 `python:3.12-slim`, 고정된 휠 여섯 개와 `app` 패키지로 구성된다. `.dockerignore`는
`tests/`를, 따라서 샘플 세이브도, 빌드 컨텍스트에서 제외한다. 서버에 있는 게임에서 유래한 것은 상수 다섯 개와
`savecheck.py`의 덧셈 하나뿐이다.

## 두 소켓의 형태

로비 소켓은 브로드캐스트 목록과 일대일 초대의 조합이다. 클라이언트가 `wait`를 보내면 변경될 때마다 연결된 모든
소켓에 `{"t":"list","users":[...]}`가 전송된다. `invite`는 한 사람에게 도달하고, `accept`는 **room**을 만들며
양쪽에 `{"t":"matched","room":id,"peer":{...},"role":"parent"|"child"}`를 보낸다.

릴레이 소켓이 바로 room이다. 바이너리 프레임은 정확히 한 피어에게 있는 그대로 전달되고, 텍스트는 `ping`/`pong`
킵얼라이브에만 사용된다. 어느 한쪽이 나가면 살아남은 쪽은 `{"t":"peer_left"}`를 받고 room은 해제된다. 프레임 형식
`[u8 kind][u8 port][u16 len][payload]`는 양쪽 끝의 WM 브리지에 속한다
(`wiki/systems/wifi-port-plan.md` section A). 서버가 이 형식을 모르는 것이 설계다. 브리지의 변경 때문에 서버를
배포할 필요가 없어야 하기 때문이다. 테스트 모음은 선언된 `len`이 페이로드와 다른 프레임을 전달하는 것으로 이를
고정한다.

**역할은 WM 역할이다.** `parent`가 비컨을 보내고 AID를 할당하므로 `parent`는 호스트("초대하는 쪽")이고 `child`는
게스트("방문하는 쪽")다. 이는 선언된 모드에서 온다. 두 피어가 같은 모드를 선언한 경우에는 -- 클라이언트는 이를
방지해야 하고 서버는 이를 신뢰해서는 안 된다 -- 실제로 일어난 일이 초대이므로 초대자가 parent가 된다.

## 세이브를 검증하며, 이것이 흥미로운 부분이다

서버가 수락했지만 게임이 열 수 없는 클라우드 세이브는 이 서비스에서 최악의 실패다. 소유자가 이미 정상적인 로컬
복사본을 바꾼 뒤 타이틀 화면에서 이를 발견하기 때문이다. 따라서 `PUT /v1/save`는 ROM 자체의 수락 테스트인
`func_020a1a40`을 실행한다. 이 테스트는 `port/shim/game/savepoll.c`에 옮겨 적혀 있으며, 서버는 이유와 함께 400을
반환한다.

* 게임 코드 바이트 `+0x0000`은 `0x32`여야 한다(`func_0209f180`).
* 플래그 바이트 `+0x173fa`는 `2`여야 한다(`func_0209fb3c`).
* 전체 `0x173fc`바이트 뱅크의 16비트 래핑 합은 `0`이어야 한다(`func_02050920`).

이는 **양쪽** 뱅크에 적용된다. 게임은 저장할 때마다 뱅크 1을 뱅크 2에 복사하며, 정상인 뱅크 하나는 쓰기가
중단된 상태이기 때문이다. 세 검사는 서로 독립적이며 각각 따로 보고된다. 뱅크가 완벽한 체크섬을 가져도 플래그
때문에 거부될 수 있다. `docs/kb/hybrid/save-flow.md`를 참조한다.

동시성은 사용자별 버전 카운터에 대한 `If-Match`이며, store의 잠금 내부에서 다시 검사한다. 두 PC가 같은 마을을
동시에 flush하면서 둘 다 자신이 성공했다고 믿을 수 없고, 패자는 조용히 덮어써지는 대신 다시 읽으라는 안내를 받는다.

## 위협 모델

공개 인터넷에 노출된 소유자의 가정이다. 공개 서비스도, 게임 보존 서버도, 다른 사람의 마을이 사는 곳도 아니다.

| 누가 | 시도할 수 있는 것 | 막는 것 |
|---|---|---|
| 도메인을 발견한 낯선 사람 | 계정 등록 | 가정의 계정이 만들어지면 `ACWW_ALLOW_REGISTER=0`으로 설정한다. 이것이 주된 통제 수단이며 README에도 두 번 나온다 |
| 비밀번호 목록을 가진 낯선 사람 | 소유자의 비밀번호 추측 | argon2id(구조적으로 느림) + IP당 분당 인증 시도 10회; `ACWW_TRUST_PROXY=1`이므로 제한은 프록시가 아닌 실제 클라이언트별이다 |
| 훔친 토큰을 가진 낯선 사람 | 해당 계정의 마을 읽기 또는 덮어쓰기 | 토큰 외에는 없다. 이는 수용한 위험이다. 무차별적인 취소 방법은 `ACWW_SERVER_SECRET`을 교체하는 것이며, 그러면 모든 토큰이 한 번에 무효화된다 |
| 로그인한 사용자 | 다른 사용자의 세이브 읽기 | 모든 세이브 경로는 토큰의 `sub`를 키로 사용하며 사용자 id를 받는 엔드포인트가 없다 |
| 로그인한 사용자 | 자신이 매칭되지 않은 room에 참여 | `accept()` 전에 room의 두 id로 멤버십을 확인하며, 제3자는 1008로 닫힌다 |
| 로그인한 사용자 | 로드되지 않을 마을 저장 | ROM의 세 부분 테스트, 양쪽 뱅크, 이유와 함께 400 |
| 로그인한 사용자 | 속여서 속도 제한을 벗어나기 | `X-Forwarded-For`는 `ACWW_TRUST_PROXY=1`일 **때만** 신뢰된다. 따라서 직접 노출된 서버는 꾸며낸 헤더로 우회할 수 없다 |
| 로그를 읽는 사람 | 비밀번호, 토큰 또는 마을 알아내기 | 명시적인 금지 필드 목록을 둔 한 줄 JSON이다. 세이브는 길이와 sha256으로만 나타난다 |
| 이미지를 얻은 사람 | 비밀 또는 게임 데이터 찾기 | 비밀은 이미지 안이 아니라 환경 변수 또는 `/data`에 있다. `tests/`와 모든 `.sav`는 빌드 컨텍스트에서 제외된다 |

**의도적으로 방어하지 않는 것.** 클라이언트는 서명되지 않은 실행 파일이므로 서버는 토큰을 가진 것이 실제 게임인지
알 수 없다. 사용자는 ROM의 테스트를 통과하는 262,144바이트라면 무엇이든 업로드할 수 있으며, 손으로 편집한 마을도
포함된다. 이는 소유자 자신의 서버에 있는 소유자 자신의 세이브 파일이다. 이를 방어하려면 클라이언트에 서명해야
하지만, 여기서는 아무것도 얻지 못한다. 토큰 폐기 목록도 갱신도 없으므로 훔친 토큰은 만료되거나 비밀이 교체될
때까지 유효하다.

## 상태가 있는 곳과 재시작에 드는 비용

| 상태 | 있는 곳 | 재시작 후 유지되는가 |
|---|---|---|
| 계정 | `/data/acww.sqlite` | 예 |
| 세이브 버전(최근 20개) | `/data/saves/...` + 각 버전의 행 하나 | 예 |
| 생성된 서명 키 | `/data/secret.key` (0600) | `/data`가 백업에 있으면 예 |
| 로비에서 대기 중인 사람 | 메모리 | 아니며, 그래야 한다 |
| 열린 room과 소켓 | 메모리 | 아니다. 두 피어가 다시 연결해 재초대한다 |

속도 제한기는 프로세스별이다. 하나의 컨테이너로 배포하는 경우에는 올바르며, 둘 이상의 replica로 실행하게 되면
옮겨야 한다. 그런 방식으로 실행하지는 않는다.

## 미해결 항목(순위순)

1. 사양의 독립형 클라이언트 부분인 `acww-online.ini`, 로그인 대화 상자, 로비 창, 릴레이 소켓을 WM 브리지에 넘기는
   부분은 아직 존재하지 않는다. 서버가 게임과 통신한 적은 없고 자체 테스트와 `server/tools/smoke.py`하고만 통신했다.
2. WM 브리지가 아직 프레임을 하나도 내보내지 않으므로 릴레이는 실제 WM 프레임을 전달한 적이 없다
   (`wiki/systems/wifi-g0.md`: 포트는 스텁 처리된 ARM7에 WM 요청을 0개 제출한다). 프레임 계약은 파이프로 구현되어
   파이프로만 입증되었다.
3. 데이터가 채워진 볼륨으로 재시작한 테스트가 없다. 컨테이너는 빈 `/data`에서 한 번 스모크 테스트되었다.
   업그레이드 인 플레이스는 테스트되지 않았다.
4. `GET /v1/save`는 256 KB 전체를 메모리로 스트리밍한다. 현재 크기와 사용자 수에서는 괜찮지만, 어느 한쪽이 커지면
   가장 먼저 바꿔야 할 부분이다.

## 클라이언트가 서버와 만난 결과 (INTEGRATE83, 2026-09-11)

MEASURED, main의 `1f6a2e36`에서 측정했다. `port/tools/test_online_integration.py`가 이 이미지를 빌드하고,
127.0.0.1:18080에서 FRESH 볼륨으로 실행한 뒤 `dist/acww.exe`를 상대로 구동한다. 게임 자체의 로그인 창으로 등록한
두 계정, 세이브 왕복, 클라이언트 모르게 버전을 써서 강제한 412, 오프라인 실행, 로비에서 만난 두 독립 프로세스,
그리고 nginx TLS 리버스 프록시를 통한 전체 과정을 다시 수행한다. 일곱 단계가 모두 통과했으며 영수증은
`scratchpad/integrate83/`에 있다.

**불일치 여섯 건을 발견했지만 이 페이지에서 고친 것은 단 하나도 없다.** 목록과 추론은
`docs/kb/hybrid/online-spec.md`의 "The two halves met" 절에 있다. 이 페이지에서 중요한 것은 서버의 논쟁적인
선택 다섯 가지가 모두 유지되었다는 점이다.

* `{"t":"list","users":[...]}` -- 클라이언트는 이제 `users`를 읽으며 사양도 `users`라고 한다.
* 정수 `user_id`와 `invite.to` / `accept.from` / `decline.from`에 대한 타입 검사. 클라이언트는 id를 인용부호로 감싸 보내고 있었고,
  거부한 것이 옳았다. 오류 메시지가 이를 찾아낼 수 있게 한 유일한 것이었으므로 -- **그 메시지를 구체적으로 유지하라.**
* ROM이 거부할 카드 이미지에 `PUT /v1/save`가 400으로 응답한다. 새 계정의 첫 실행은 예전에 매 세션마다 하나를
  보냈지만, 이제 클라이언트가 PUT 전에 같은 테스트를 실행한다.
* `{"t":"peer_left"}`와 생존자에 대한 1000 close. 클라이언트에는 어느 쪽에도 대응하는 분기가 없었다.
* 버퍼 없이 릴레이가 전달하거나 버리는 동작. 클라이언트의 일회성 프로브가 피어의 연결과 경합해 실패했으며,
  릴레이가 아니라 INSTRUMENT를 변경했다.

이 실행은 운영에 관해 두 가지를 말해 준다.

* **구조화된 이벤트가 통합 근거다.** `auth.login`, `save.put`(`if_match` 포함), `save.stale`, `save.rejected`,
  `lobby.matched`(`parent` / `child` 포함), `relay.close`(`frames_forwarded` 포함)를 fixture가 검증한다.
  uvicorn의 액세스 줄만으로는 충분하지 않다. 더 조용하게 만들지 마라.
* **`docker logs`는 stdout과 stderr를 인터리브하지 않고 두 블록으로 반환한다.** JSON 이벤트는 stdout에, uvicorn의
  액세스 로그는 stderr에 있다. "지금부터의 로그"를 읽는 것은 둘을 따로 표시해야 한다.

### 측정된 리버스 프록시

이 페이지가 가정하는 배포, 즉 "TLS는 NAS 리버스 프록시의 일이다"는 이제 웹소켓을 전달하는 것으로 알려진 설정을
갖추었다. 설정은 `scratchpad/integrate83/tls/acww.conf`에 있고 fixture에도 인라인으로 들어 있다. 이를 결정하는
세 줄은 `proxy_http_version 1.1`, `Upgrade`/`Connection` 쌍(`map $http_upgrade $connection_upgrade`와 함께 사용하며, 상수
`Connection: upgrade`는 모든 일반 요청을 망가뜨리므로), 그리고 유휴 로비 소켓에 충분히 긴 `proxy_read_timeout`이다.
이를 잘못 설정하면 클라우드 세이브는 계속 작동하지만 로비는 조용히 작동하지 않으며, 이는 이 서비스가 실패할 수
있는 최악의 형태다.

프록시 뒤에서는 `ACWW_TRUST_PROXY=1`이 여전히 중요하다. 그렇지 않으면 속도 제한기가 한 클라이언트로 본다.
